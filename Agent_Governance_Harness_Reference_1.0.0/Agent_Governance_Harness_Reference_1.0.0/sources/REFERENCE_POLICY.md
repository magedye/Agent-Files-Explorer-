# Reference policy

## Source selection
Start with the developer responsible for the model or host under consideration. Verify publisher, product, release or snapshot, applicable feature, document type, retrieval date and explicit deprecation/supersession. Use secondary sources only as clearly labeled supplemental evidence; none is required for this baseline. Owner decisions are identified separately from vendor references.

## Applicability and limits
A protocol reference may define valid fields; a best-practice article may recommend a strategy; an experiment reports what worked in one environment. Their scopes differ. Do not copy sample insecure logging, unbounded loops, broad permissions, version aliases, permissive merge behavior or historical defaults as mandatory production policy. Official technical priority is not institutional supremacy or authority to execute tools.

## Freshness
At adoption and whenever a relevant model, endpoint, SDK, host, permission mode or security advisory changes, recheck the affected primary sources. Keep the previous reference record and document the accepted change. Retrieval date is not publication date. Absence of a publication date is recorded as null, not invented. Offline use is supported for this reference; changed product behavior requires reconfirmation before relying on it.

## Citations and independence
REGISTER.json provides stable IDs, URLs, section locators, dates and bounded original summaries. Contracts and adapters cite those IDs. No external article is copied wholesale; this package is original synthesis, not an official vendor standard. The earlier conversation's study is a set of claims to verify, not a source of automatic authority.

## Conflict procedure
Check issuer jurisdiction, feature scope, status and explicit replacement. Prefer the applicable specification over an illustrative example where they address the same semantics. Preserve unresolved alternatives and stop the affected action only. Record security constraints that prevent implementing a technically supported capability.
