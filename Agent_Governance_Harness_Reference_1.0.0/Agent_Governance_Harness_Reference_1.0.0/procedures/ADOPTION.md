# Adoption procedure — new and existing projects

**Trigger:** explicit authorization to prepare or apply governance to a project. **Owner:** project authority. **Inputs:** this exact package candidate, project scope, existing instructions, repository/environment evidence. **Output:** reconciled project operating contract and a scoped adoption/qualification record.

1. **Discover read-only.** Identify product type, existing instruction files including managed/global/nested content, authoritative requirements, Git state, real commands, agents, data and deployment boundaries. Preserve unknowns. An archive or folder is not automatically trusted.
2. **Select profile and routes.** STANDARD by default; check LITE eligibility or CONTROLLED boundaries. Select provider and host independently. Record actual versions/capabilities and official references. No automatic creation of unsupported context files.
3. **Prepare isolated records.** Run runtime/cli.py init or use the templates with an established tracker. Initialization creates proposals only and never overwrites an existing `.aghr`. Keep a rollback inventory of files that adoption is authorized to create/change.
4. **Reconcile.** Classify each existing rule: KEEP, LINK, MERGE, REPLACE_BY_DECISION, CONFLICT or HISTORICAL. Preserve legitimate stronger project-specific obligations. Do not automatically supersede local instructions because this package is newer. Record intentional semantic differences.
5. **Authorize the effective scope.** Identify the decision owner and adoption reference, version/hash, affected repository/environment, allowed work and exclusions. If the current request already authorizes the relevant low-risk writes, continue; ask only for missing authority or unresolved consequential conflict.
6. **Apply narrowly.** Merge the approved entry router into the actual supported host instruction file; configure permissions in the host's real protected settings through the authorized operator. Never replace global configuration or broad permissions as a shortcut. Preserve existing files and record exact changes.
7. **Qualify.** Run structural readiness checks and the host procedure. Test the real loaded context and permitted/denied effects in isolation. A fake approval string or dry-run refusal is not host qualification. Record NOT_RUN when the environment is unavailable.
8. **Decide and hand off.** The competent owner records effectiveness for the proven scope. Deliver changes, checks, limits and rollback/resume procedure. Production activation and release remain separate if applicable.

## State model
PREPARED: proposals and discovered gaps exist. CONFIGURED: approved files/settings have been applied and their structure checked. EFFECTIVE: authorized adoption plus applicable host evidence supports the declared operating scope. These are adoption states only, not test outcomes. The initializer sets PREPARED; validators never authenticate approval or promote a state automatically.

## Exact acceptance
No existing unrelated bytes changed; relevant source conflicts resolved or isolated; facts are actual rather than sample defaults; required host routes are qualified; reference and records are locally accessible; instruction routing works; the operator knows stop/recovery and intake paths. An unknown high-risk boundary prevents that action, not use of the reference for safe review.

## Agent request
Use prompts/ADOPT.md. It contains discovery, proposal-only and authorized-application behavior in one prompt, without repeated permission loops.
