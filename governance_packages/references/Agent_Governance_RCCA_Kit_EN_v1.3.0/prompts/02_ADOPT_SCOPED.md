# Scoped project adoption — proposal first, apply only when already authorized

Reconcile this candidate kit with the existing project's governing sources and effective host instructions.
The owner has not authorized adoption merely by providing the archive. Identify the actual current grant, allowed
writes and protected artifacts. If that grant explicitly includes adoption, implement the approved minimal diff;
otherwise deliver the proposed diff and decisions without changing the project.

Use one primary instruction entrypoint, the existing task/request record and the existing owner-decision mechanism.
Do not create parallel task databases, approval registries or copies of every rule. Select the core and only relevant
rules. Authority, impact, normative force, applicability, lifecycle and technical permissions are separate fields.
Preserve source authority; a later package version is not an automatic supersession.

For one developer and one primary agent, establish a task-bound broad local grant: reversible in-scope edits,
focused tests/builds, justified local dependency work, recovery and local commits where explicitly included.
Keep sensitive/external actions separately scoped. Do not invent extra staff or require a second agent for normal
R0/R1 work. Retain honest self-review labels and owner decisions for protected boundaries.

Verify effective host discovery and permissions; use the exact Codex/Antigravity/OpenCode version. Do not change
global configuration, install tools, enable hooks, grant network access or push/deploy without their own authority.
Preserve unrelated changes. Report changed files, authority mapping, what remains inert, tests actually run and a
safe reversal of only the adoption diff. Do not reset the worktree or overwrite newer owner work to roll back.
