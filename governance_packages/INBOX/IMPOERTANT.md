# تقييم مهارة Aprende وعلاقتها بحوكمة AGHR

أرى أن مهارة [Aprende](https://github.com/Hainrixz/aprende-skill/blob/main/skills/aprende/SKILL.md) ذات قيمة عالية لمشروع AGHR، لكنني لا أوصي بتثبيتها كما هي باعتبارها مهارة حاكمة. أوصي بالاستفادة من منهجيتها لبناء قدرة موحدة لإدارة الدروس المستفادة (Governed Learning Lifecycle)، مع إعادة استخدام مهارات `/learn` الموجودة لدى الوكلاء.

بعد قراءة `SKILL.md` من المستودع الفعلي، يتضح أن أهمية Aprende لا تقتصر على حفظ الملاحظات. إنها تعالج مشكلة جوهرية في عمل الوكلاء: كيف نحول التجارب والأخطاء وتصحيحات المستخدم إلى معرفة دائمة ومفيدة دون ترسيخ استنتاجات غير صحيحة؟

وهذا بالفعل من صميم حزمة AGHR، لكنه يتطلب فصل التعلم عن السلطة والاعتماد والتنفيذ.

## 1. ماذا تقدم مهارة Aprende فعليًا؟

تعتمد المهارة الإصدار `0.1.0`، بترخيص MIT، وتستخدم خمس مراحل متتابعة:

1. Scan — الاكتشاف: استخراج التصحيحات والأخطاء المتكررة وأسباب الفشل وسلوكيات التنفيذ المهمة من المحادثة.
2. Generate — توليد المرشحات: صياغة دروس مقترحة وتصنيفها مع درجة ثقة ومصدر.
3. Dedup — كشف التكرار: مقارنتها بالذاكرة والمهارات وتعليمات المشروع الموجودة.
4. Confirm — التأكيد: عرض المرشحات على المستخدم قبل إجراء أي كتابة.
5. Execute — الحفظ: توزيع العناصر المقبولة إلى الذاكرة أو سجل الدروس أو Skill أو وثائق المشروع.

وتصنّف النتائج إلى أربعة أنواع:

| النوع         | وظيفته                                           |
| ------------- | ------------------------------------------------ |
| `memory`      | معلومات دائمة عن المشروع أو تفضيلات المستخدم     |
| `lesson`      | خطأ حدث، وسببه، وكيفية تفادي تكراره              |
| `skill`       | إجراء متعدد الخطوات يصلح لإعادة الاستخدام        |
| `project-doc` | معلومة تشغيلية ينبغي أن يعرفها الوكيل في المشروع |

كما تدعم `/aprende --review` لمراجعة الدروس القديمة، و`--portable` لإنشاء نسخة مشتركة داخل المشروع.

## 2. أهم ما يستحق اقتباسه في AGHR

| قدرة Aprende                                   | قيمتها للحزمة | توصية الإدماج                                                               |
| ---------------------------------------------- | ------------- | --------------------------------------------------------------------------- |
| استخراج الدروس من تصحيحات المستخدم             | عالية         | اعتمادها ضمن مرحلة اكتشاف المرشحات                                          |
| توثيق المشكلة والسبب وطريقة المنع وإشارة الكشف | عالية جدًا    | اعتماد نموذج درس موحد                                                       |
| كشف التكرار قبل الحفظ                          | عالية         | توسيعه ليشمل العقود والقواعد والقرارات والاختبارات                          |
| مراجعة الدروس وتقادمها                         | عالية         | إدخال حالات حياة الدرس وإعادة التحقق                                        |
| تأكيد المستخدم قبل الكتابة                     | عالية         | تطبيق الموافقة بحسب السلطة والنطاق، دون مطالبة متكررة عندما يوجد تفويض صالح |
| تحويل سير العمل المتكرر إلى Skill              | مفيد          | إنشاء مهارة جديدة فقط عند ثبوت عدم كفاية الموجود                            |
| حفظ الدروس عبر أدوات مختلفة                    | مفيد          | استخدام سجل مشروع محايد عن المضيف مع موائمات تقنية                          |

الميزة الأهم بنظري هي نموذج الدرس الذي يحتفظ بأربعة عناصر: What happened / Why / How to avoid / Detection signal.

هذا أكثر فائدة من سجل يكتفي بكتابة «يجب ألا يكرر الوكيل الخطأ»، لأنه يوفر أساسًا لتحويل الدرس إلى اختبار أو ضابط قابل للتنفيذ.

## 3. أين تتعارض Aprende مع حوكمة AGHR؟

توجد خمسة جوانب تمنعني من التوصية بتثبيتها كما هي:

| المسألة                           | السلوك الحالي في Aprende                                       | ما تحتاجه AGHR                                                          |
| --------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------- |
| ترقية الدروس إلى تعليمات          | بعد تأكيد المستخدم يمكن كتابة الدرس في `AGENTS.md`             | يجب التحقق من السلطة والنطاق والاعتماد قبل تغيير سياسة حاكمة            |
| ازدواجية الوثائق                  | تكتب النص نفسه في `CLAUDE.md` و`AGENTS.md`                     | مصدر معياري واحد مع موائمات أو إحالات متوافقة مع المضيف                 |
| تعدد مصادر الذاكرة                | تستخدم `~/.claude/projects/` وقد تنشئ `.aprende/` داخل المشروع | تكامل مع سجل الدروس والحالة القائمين، دون إنشاء مصدر حقيقة منافس        |
| إنشاء Skills تلقائيًا بعد التأكيد | قد تنشئ Skill أولية ناقصة (Stub)                               | تقييم الحاجة، وفحص الموجود، وتأهيل المهارة قبل اعتبارها قابلة للاستخدام |
| Hooks والوصول إلى المحادثات       | توفر Hooks مفعّلة افتراضيًا في إعدادات الإضافة                 | فحص الخصوصية والصلاحيات والاحتفاظ قبل تشغيل المراقبة                    |

وهناك ثلاث ملاحظات إضافية:

أولًا: درجة الثقة `high` في Aprende قد تنشأ من تصحيح صريح للمستخدم. وهذا مناسب لتحديد احتمال أن الوكيل فهم كلام المستخدم، لكنه لا يثبت صحة الاستنتاج الهندسي أو صلاحيته للتعميم.

ثانيًا: تعتمد على مراجعة المحادثة وإشارات الأخطاء، وقد تلتقط سلوكًا عرضيًا لا يمثل سببًا جذريًا مثبتًا. يجب أن تُربط الدروس المهمة بنتائج الاختبارات والتغييرات والمراجع المعتمدة، لا بالمحادثة وحدها.

ثالثًا: وجود الموافقة على حفظ درس لا يعني بالضرورة الموافقة على تعديل سياسة عامة أو نشر مهارة. يجب فصل اعتماد محتوى الدرس عن تفويض الكتابة وعن تفعيل أثره.

لذلك فإن التعديل المطلوب ليس مجرد إضافة فحص للتكرار، بل إضافة طبقة مصالحة حوكمية بين اكتشاف الدرس وإدماجه.

## 4. المعمارية التي أوصي بها لحزمة AGHR

أوصي بقدرة عامة باسم Governed Learning & Continuous Improvement تتعامل مع وظائف `/learn` و`/aprende` وأدوات التقاط الدروس الموجودة باعتبارها وسائل لجمع المرشحات، لا جهات تمنح سلطة.

ويجب أن يدعم كل درس حالتين منفصلتين:

- حالة المعرفة: مرشح، مثبت، يحتاج مراجعة، متقادم، مستبدل، مرفوض.
- حالة التصرف: لم يُنفذ، أُدمج في مرجع، تحوّل إلى اختبار، أُجّل، أو يحتاج اعتمادًا.

وبذلك لا يصبح الدرس «قاعدة» لمجرد حفظه.

## 5. أين ينبغي إدماج هذه القدرة؟

أقترح هذا التوزيع داخل حزمة AGHR، مع إعادة استخدام الملفات الموجودة أولًا:

| المكون             | الوظيفة المطلوبة                                           |
| ------------------ | ---------------------------------------------------------- |
| سياسة تطور الحوكمة | شروط تحويل الدرس إلى قاعدة عامة                            |
| إجراء إدارة الدروس | اكتشاف الدروس ومراجعتها وتصنيفها ومصالحتها وتحديد التصرف   |
| قالب Lesson Record | المشكلة والدليل والسبب الجذري وإشارة الكشف والتصرف والسلطة |
| مهارات الوكلاء     | موائمات لاستخدام `/learn` أو غيرها دون اعتماد تلقائي       |
| أدوات التحقق       | كشف التكرار والاستبدال غير الصحيح والعلاقات الناقصة        |
| سجل الأدلة         | ربط الدرس بنتائج التجارب والاختبارات ونسخ التنفيذ          |

أما مجلد `_INBOX/` الذي اتفقنا عليه فيمكن استخدامه لاستقبال ملفات الدروس الخارجية أو تقارير الجلسات، مع بقاء الملفات غير موثوقة وغير معتمدة حتى انتهاء المصالحة.

## 6. الطلب الذي أوصي بتقديمه لوكيل AGHR

# طلب تقييم ودمج منهجية Aprende ضمن حوكمة التعلم المستمر في AGHR

**المشروع:** Agent Governance Harness Reference — AGHR\
**المدخل:** مهارة `aprende` من المستودع `https://github.com/Hainrixz/aprende-skill`، مع مهارات `/learn` المتاحة لدى المضيفين.\
**النطاق:** تطوير حزمة AGHR المرشحة بصورة مستقلة عن مشاريعها المستفيدة.

راجع مهارة Aprende ومراجعها وآليات Hooks والحفظ والمراجعة، وقارنها بالعقود والقواعد والسياسات والإجراءات والمهارات والاختبارات الموجودة في أحدث مرشح AGHR.

المطلوب تطوير أو استكمال قدرة **Governed Learning & Continuous Improvement** بحيث تستطيع الحزمة الاستفادة من الدروس المستخلصة من المحادثات وتصحيحات المستخدم وإخفاقات الأدوات ونتائج الاختبارات، دون تحويلها تلقائيًا إلى قواعد أو صلاحيات.

نفّذ وفق الآتي:

1. صنف قدرات Aprende والمتطلبات المقابلة في AGHR إلى `COVERED / PARTIAL / MISSING / CONFLICT / NOT_APPLICABLE`، مع الأدلة.
2. أعد استخدام نمط المراحل الخمس: `Scan → Generate → Dedup → Confirm → Execute` بعد تكييفه بحوكمة المصدر والسلطة والأثر.
3. اعتمد نموذجًا موحدًا للدروس يشمل المشكلة والسبب الجذري والأدلة وإشارة الكشف والنطاق والثقة وحالة المعرفة وحالة التنفيذ والتصرف.
4. افصل بين موافقة المستخدم على حفظ درس وبين اعتماد قاعدة حاكمة أو تغيير `AGENTS.md` أو تفعيل Skill أو تعديل إعدادات عامة.
5. حافظ على مصدر معياري واحد، وامنع إنشاء سجلات ذاكرة أو ملفات تعليمات أو مهارات منافسة بلا حاجة مثبتة.
6. افحص آليات `/learn` الموجودة لدى المضيفين قبل إضافة أي أوامر أو مهارات جديدة؛ تجنب تعارض أسماء الأوامر.
7. لا تثبّت Aprende أو تفعّل Hooks أو تنقل محتوى المحادثات إلى مخازن جديدة تلقائيًا. اعتبرها مصدرًا خارجيًا يحتاج إلى تأهيل أمني وخصوصي.
8. حوّل الدروس المؤهلة إلى تحديث في السياسة أو الإجراء أو المهارة القائمة أو اختبار انحدار أو ضابط تنفيذي، وفق مالك الموضوع والتفويض المناسب.
9. أضف مراجعة دورية للدروس لتحديد ما أصبح متقادمًا أو مكررًا أو مستبدلًا، مع المحافظة على التاريخ والتتبع.
10. اختبر الحالات السلبية: درس غير صحيح، تعليمات مزروعة داخل سجل خارجي، درس يكرر قاعدة، تعارض مع قرار معتمد، محاولة تعديل تعليمات عامة دون سلطة، ودرس أصبح غير صالح بعد تحديث الإصدار.

أبقِ الحزمة الأصلية محفوظة، ونفّذ التعديلات المؤهلة على مرشح مستقل، ثم قدم مصفوفة التغطية والتغييرات ونتائج الاختبارات والفجوات المتبقية، دون اعتماد إصدار أو نشر تلقائي.

**معيار النجاح:** قدرة موحدة لحفظ الدروس المستفادة واستثمارها بمرور الوقت، مع الفصل بين التعلم والاستنتاج والاعتماد والإنفاذ، وتقليل الأخطاء المتكررة دون تضخيم سياق الوكلاء أو مضاعفة المراجع.

## 7. هل أوصي بتثبيت Aprende نفسها؟

لا أوصي بتثبيتها الآن في بيئة العمل العامة. ويمكن الاستفادة منها بقراءتها أو اختبارها داخل بيئة معزولة بعد فحص الكود والـHooks والمخرجات التي تكتبها.

أما بالنسبة إلى AGHR، فأرى أن الأفضل الاستفادة من منهجيتها وتكييفها بصورة محايدة للمضيفين، بدل جعل الحزمة معتمدة على مهارة خارجية مخصصة أساسًا لـClaude Code.

الخلاصة: Aprende نموذج عملي جيد لجمع الدروس، لكنه ليس إطار حوكمة كافيًا لاعتماد تلك الدروس. والقيمة الحقيقية لـAGHR ستكون في إضافة طبقة تتحقق من صحة الدرس وسلطته وأثره، ثم تختار المكان الصحيح لاستثماره — قاعدة، إجراء، Skill، اختبار، أو مجرد معرفة محفوظة.

لم أعدّل أي مستودع أو أثبّت أي إضافة في هذه المراجعة. وتبقى صلاحية المهارة للعمل على مضيف معين بحاجة إلى اختبار فعلي في ذلك المضيف.



أقوى مهارة هي **“Session Retrospective & Lessons-Learned Harvester”**: مهارة/بروتوكول إلزامي يجعل الوكيل يستخرج في نهاية كل جلسة الدروس، الأخطاء، القرارات، والقيود، ثم يحوّلها إلى ذاكرة دائمة قابلة للاستخدام في الجلسات التالية. الأهم أنها ليست مجرد “تلخيص”، بل **إجبار الوكيل على إثبات الدرس من الأدلة وتحويله إلى قاعدة تنفيذية**. ## لماذا هي الأقوى؟

لأنها تعالج المشكلة الحقيقية في مشاريع البرمجة مع الوكلاء: تكرار الأخطاء، نسيان القرارات المعمارية، وضياع السياق بين الجلسات. تصميم الذاكرة بشكل متعمّد هو من أفضل ممارسات هندسة الوكلاء، لأنه ينقل المعرفة والقرارات عبر الجلسات والبيئات. [exabeam](https://www.exabeam.com/ar/explainers/agentic-ai/agentic-ai-architecture-types-components-best-practices/)

المهارة يجب أن تفرض على الوكيل أربعة مخرجات إلزامية:

- **Facts**: ما حدث فعليًا، مع ملفات، أوامر، ونتائج اختبار.
- **Root causes**: لماذا فشل الحل أو نجح.
- **Decisions**: القرار المعماري أو التقني المتخذ وسببه.
- **Rules for next sessions**: تعليمات قابلة للتنفيذ مثل “لا تستخدم X”، “افحص Y قبل النشر”، أو “استخدم نمط Z”.

## اسم المهارة المقترح

`lessons-learned-enforcer`

أو بالعربية: **مستخرج الدروس الإلزامي للجلسات البرمجية**.

هذه المهارة تُشغَّل تلقائيًا عند:
- إنهاء جلسة برمجية.
- حل Bug معقد.
- اتخاذ قرار معماري.
- فشل اختبار أو نشر.
- اكتشاف قيد في البيئة أو الأدوات.

## قالب الأمر الجاهز

أضف هذا إلى `AGENTS.md` أو system prompt الوكيل:

```text
MANDATORY: At the end of every coding session, before stopping, run the
"lessons-learned-enforcer" skill.

You must extract lessons from this session and persist them to the project
knowledge base. Do not produce a generic summary.

For every meaningful issue, failure, fix, decision, or discovery, output:

1. LESSON
   - Short, actionable statement.

2. EVIDENCE
   - Exact file(s), command(s), error message(s), test result(s), or URL(s).

3. ROOT CAUSE
   - Why the issue occurred or why the solution worked.

4. DECISION
   - What we will do differently next time.

5. RULE
   - Convert the lesson into a durable rule for future sessions.
   - Use one of: MUST, MUST NOT, SHOULD, PREFER, AVOID.

6. TARGET MEMORY
   - Choose one: project_rules, architecture_decisions, coding_standards,
     deployment_runbook, debugging_playbook, security_controls, user_preferences.

7. CONFIDENCE
   - high / medium / low, with reason.

Rules:
- Never invent evidence.
- If evidence is incomplete, mark confidence as low and ask for confirmation.
- Reject vague lessons such as "be careful" or "improve quality".
- Every lesson must be specific, testable, and reusable.
- After extraction, update the relevant persistent memory files.
- Finally, print a compact "Next Session Startup Brief" containing only the
  rules and constraints relevant to the next task.
```

## مثال على مخرَج قوي

```text
LESSON:
Docker Compose health checks must wait for MSSQL to accept connections before
starting the API container.

EVIDENCE:
- docker-compose.yml
- API failed with: "SqlException: Cannot open database"
- Health check returned unhealthy for 38 seconds.

ROOT CAUSE:
The API started before MSSQL completed initialization.

DECISION:
Use depends_on with condition: service_healthy and a proper MSSQL health check.

RULE:
MUST NOT start application containers before database health checks pass.

TARGET MEMORY:
deployment_runbook

CONFIDENCE:
high — reproduced and verified by successful startup after fix.
```

## كيف تجعلها “تجبر” الوكيل؟

اجعلها جزءًا من **Definition of Done**، لا اختيارية:

```text
A coding session is not complete until:
1. All code changes are tested.
2. Lessons Learned extraction has run.
3. Relevant project memory files are updated.
4. A Next Session Startup Brief is produced.
```

وفي بداية كل جلسة، أمر الوكيل بقراءة الذكرة أولًا:

```text
Before writing code:
1. Read project_rules.md, architecture_decisions.md, debugging_playbook.md,
   and deployment_runbook.md.
2. List only the rules relevant to the current task.
3. State how you will avoid previously recorded failures.
4. Then proceed.
```

هذا يحوّل الدروس من ملاحظات عابرة إلى **قيود تشغيلية** تُطبَّق فعليًا في الجلسات القادمة. المهارات المنظمة تُستخدم أيضًا لتحويل ملاحظات المراجعات الرجعية إلى صيغة موحّدة قابلة للتكرار. [clickup](https://clickup.com/ar/blog/622661/claude-skills-project-management)

## البنية المقترحة للذاكرة

```text
/docs/agent-memory/
  project_rules.md
  architecture_decisions.md
  coding_standards.md
  debugging_playbook.md
  deployment_runbook.md
  security_controls.md
  lessons/
    2026-10-16-session.md
```

- `project_rules.md`: قواعد دائمة للمشروع.
- `architecture_decisions.md`: قرارات معمارية مع السبب والبديل المرفوض.
- `debugging_playbook.md`: أخطاء متكررة وحلولها المجربة.
- `deployment_runbook.md`: خطوات النشر، الفحوصات، والقيود.
- `lessons/`: سجل زمني كامل لكل جلسة.
