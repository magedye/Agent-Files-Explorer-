# Skill selection examples and using-agent-skills alignment

These JSON files are synthetic templates, not inventory exports or grants. [HOST_INVENTORY](HOST_INVENTORY.json) deliberately leaves availability UNKNOWN; [TASK](TASK.json) and [CONTEXT](CONTEXT.json) demonstrate local preparation. Actual host identity/version/visibility and project facts must be observed before relying on a descriptor.

`using-agent-skills` can help choose development workflows when already available in the host. Keep the native copy and its owner; do not install/copy/edit it through this example. A qualified ID and scoped project preference may point to it without duplicating its SKILL.md.

## Alignment checklist

- Higher host instructions and the project's actual authority remain effective. A routing guide cannot grant tools, replace accepted requirements or waive checks.
- Evaluate the active phase and select only relevant available workflows. No compulsory full development pipeline for simple work.
- Reconcile missing referenced skills, optional tools, overlapping names and broken references. A missing route is a recorded limitation, not an automatic install request or simulated invocation.
- Preserve the distinction between metadata, local instruction reading, native loading, execution and outcome evidence. Host internals may be NOT_OBSERVABLE.
- Continue independent authorized work when one route is blocked. Do not convert a permission denial into permission for direct execution.
- After a meaningful correction, use the existing learning procedure. No automatic global memory, policy amendment or new skill creation.

Use the existing project configuration's selection section or [the small template](../../templates/SKILL_SELECTION.json). Follow [the runtime contract](../../runtime/SKILLS.md) and [capability review](../../procedures/EXTERNAL_CAPABILITIES_AR.md); no separate router service is needed.
