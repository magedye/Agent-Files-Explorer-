# لوحة تحكم المالك لمراجعة وحوكمة قواعد وكلاء الذكاء الاصطناعي
سأعيد تقديم الإجابتين بمنظور مستقل تمامًا، دون افتراض وجود أي منصة حوكمة سابقة.

الهدف هو إنشاء منظومة عملية لإدارة ومراجعة وتحسين قواعد وبنود حوكمة الذكاء الاصطناعي، تعتمد على AAPES v2.1، وتمنح المالك أدوات لاتخاذ قرارات دقيقة بشأن أهمية كل بند وضرورته وأثره وإمكانية دمجه أو تعديله أو استبعاده.

سأتعامل مع 423 بندًا باعتبارها العدد المذكور في المعطيات، لا عددًا تحققت منه بإعادة فحص المصنف.

# الإجابة الأولى: ماذا يمكنك فعله ومراجعته بصفتك المالك وصاحب القرار؟

## 1. الانتقال من إنشاء البنود إلى إدارتها

بعد جمع مئات البنود، لا ينبغي أن يكون الهدف التالي إنتاج المزيد منها، ولا تقليل عددها لمجرد الاختصار.

الهدف الصحيح هو تحويل البنود إلى منظومة حوكمة متماسكة، قليلة التكرار، واضحة السلطة، قابلة للتنفيذ والاختبار، ومبررة من حيث القيمة والتكلفة.

يجب أن تساعدك المنظومة على الإجابة عن الأسئلة التالية:

| السؤال                 | ما الذي تحتاج إلى معرفته؟                          |
| ---------------------- | -------------------------------------------------- |
| لماذا يوجد هذا البند؟  | الغرض والمشكلة التي يعالجها                        |
| هل البند ضروري؟        | ما الذي يحدث إذا غاب أو أُلغي؟                     |
| ما أهميته؟             | مستوى المخاطر والقيمة والأولوية                    |
| هل صيغته صحيحة؟        | الوضوح والذرية والدقة الدلالية                     |
| هل يوجد تكرار؟         | البنود التي تغطي الالتزام نفسه                     |
| هل يمكن دمجه؟          | إمكانية توحيده دون فقدان التزامات أو استثناءات     |
| ما أثر تعديله؟         | العلاقات والتبعيات والتغير المتوقع في السلوك       |
| هل يمكن إثبات فائدته؟  | الأدلة ونتائج الاختبارات                           |
| هل يستحق تكلفة تطبيقه؟ | التعقيد والأداء والعبء التشغيلي                    |
| ما القرار المناسب؟     | إبقاء أو تحسين أو تقسيم أو دمج أو استبعاد أو تأجيل |

## 2. ما القرارات التي ينبغي أن تحتفظ بها بصفتك المالك؟

أوصي بفصل القرارات إلى خمسة أنواع:

| نوع القرار          | مسؤوليتك                                                                                  |
| ------------------- | ----------------------------------------------------------------------------------------- |
| Normative Decision  | تحديد ما إذا كان البند إلزاميًا `MUST` أو توجيهيًا `SHOULD` أو اختياريًا `MAY`، ضمن سلطتك |
| Structural Decision | اعتماد تقسيم البند أو دمجه أو نقله إلى مجال آخر                                           |
| Priority Decision   | تحديد الأهمية والأولوية والمخاطر المقبولة                                                 |
| Acceptance Decision | اعتماد الصياغة أو خطة الاختبار أو قبول مخاطر متبقية                                       |
| Activation Decision | التصريح بتطبيق البند وتفعيله بعد استيفاء الشروط                                           |

يمكن للذكاء الاصطناعي إعداد التحليل والتوصيات والبدائل، لكنه لا ينبغي أن يمنح نفسه سلطة الاعتماد.

كما ينبغي عدم الخلط بين اعتماد صياغة البند واعتماد تطبيقه؛ فقد يكون صحيحًا من حيث المتطلبات، لكنه لم يخضع بعد لاختبارات كافية.

## 3. بطاقة مراجعة البند — Rule Review Card

أنصح بإنشاء بطاقة موحدة تعرض لك جميع المعلومات اللازمة لاتخاذ القرار.

## RULE-042

مثال افتراضي — حماية الملفات الحساسة

P0

النص الأصلي

يمنع الوكيل من تعديل الملفات الحساسة دون موافقة.

| المجال         | Security & Authorization                |
| -------------- | --------------------------------------- |
| الإلزام        | MUST NOT                                |
| الأهمية        | مرتفعة — تقدير أولي                     |
| قابلية الإنفاذ | تحتاج آلية صلاحيات مستقلة               |
| دليل الفاعلية  | NOT VERIFIED                            |
| إمكانية الدمج  | تحتاج مقارنة ببنود الموافقات والصلاحيات |

توصية المراجعة

إعادة صياغة البند لتعريف الملفات الحساسة والموافقة الصالحة، وربطه بضابط صلاحيات خارجي.

هذا النموذج يوضح شكل بطاقة القرار، ولا يمثل تحليلًا منفذًا على بند فعلي.

من المفيد أن تسمح البطاقة بعرض النص السابق والنص المقترح جنبًا إلى جنب، والانتقال إلى البنود المرتبطة، وفتح دليل كل نتيجة، وتسجيل قرار المالك ومبرراته.

## 4. كيف تقرر أن بندين قابلان للدمج؟

هذه إحدى أهم وظائف منظومة المراجعة.

لا يكفي وجود كلمات متشابهة بين بندين. يجب تحليل العلاقة بينهما:

| نوع العلاقة         | التفسير                               | الإجراء المناسب                   |
| ------------------- | ------------------------------------- | --------------------------------- |
| Exact Duplicate     | تكرار كامل لنفس الالتزام              | توحيد النسخة المرجعية             |
| Semantic Equivalent | اختلاف الصياغة مع تكافؤ الالتزام      | دمج بعد التحقق                    |
| Subsumption         | بند عام يشمل بندًا متخصصًا            | ربط هرمي أو توحيد مشروط           |
| Complementary       | بندان يكمل أحدهما الآخر               | تجميع دون حذف الالتزامات المستقلة |
| Conflict            | تعارض في السلوك أو الشرط أو الاستثناء | حسم التعارض                       |
| Independent         | أهداف أو متطلبات مختلفة               | الإبقاء عليهما مستقلين            |

### مثال

البند الأول:

> لا يجوز تعديل بيانات الإنتاج دون موافقة معتمدة.

البند الثاني:

> يجب التحقق من صلاحية الموافقة قبل تنفيذ تعديل بيانات الإنتاج.

البندان متقاربان، لكن الأول يفرض شرط وجود الموافقة، والثاني يفرض التحقق من صحتها.

التوصية: تجميعهما ضمن سياسة واحدة، مع المحافظة على الالتزامين كمتطلبين قابلين للاختبار بصورة مستقلة.

وهذا يقود إلى تمييز مهم:

- Consolidation: تجميع تنظيمي للبنود.
- Normative Merge: استبدال التزامات أصلية بالتزامات موحدة بعد إثبات عدم فقدان أي شرط.

الدمج التنظيمي أقل مخاطرة عادةً من الدمج المعياري.

## 5. كيف تقيس أهمية وتأثير كل بند؟

أوصي بالفصل بين أربعة مؤشرات:

| المؤشر              | السؤال الذي يجيب عنه                | طريقة التقدير أو القياس |
| ------------------- | ----------------------------------- | ----------------------- |
| Importance          | ما أهمية وجود البند؟                | تقييم المخاطر والأهداف  |
| Expected Impact     | ما الأثر المتوقع من تطبيقه؟         | تحليل هندسي قبل التجربة |
| Measured Impact     | هل أثبتت الاختبارات تأثيرًا فعليًا؟ | تجارب مقارنة وAblation  |
| Implementation Cost | ما تكلفة تطبيقه والمحافظة عليه؟     | الجهد والأداء والصيانة  |

ولا أنصح بمنح البند درجة مركبة واحدة دون الاحتفاظ بمكونات تقييمها.

على سبيل المثال، قد يكون بند ما:

- عالي الأهمية.
- منخفض الأثر المقاس لأن ضابطًا آخر يغطي وظيفته.
- مرتفع التكلفة.
- مناسبًا للدمج أو توحيد الإنفاذ، لا للحذف المباشر.

كذلك، يجب اعتبار أوزان AAPES أوزانًا تصميمية قابلة للمعايرة، لا نسبًا تجريبية مثبتة لتحسن أداء النموذج.

# الإجابة الثانية: تقييم الأدوات المقترحة وأفضل منظومة للمراجعة والدمج

## 1. قراري بشأن الأدوات

أوصي ببناء بيئة مراجعة مستقلة للمالك (Owner Governance Review Workspace)، يكون مصدر بياناتها ملف Excel الحالي، وتستخدم AAPES v2.1 منهجًا للتصنيف والتقييم.

يمكن البدء دون تطوير تطبيق جديد باستخدام Excel وأداة تحليل بالذكاء الاصطناعي، ثم بناء واجهة مخصصة إذا أصبحت المراجعات عملية متكررة.

ولا أوصي بتطبيق جميع الأدوات المذكورة في المقترح؛ لأنها تغطي وظائف مختلفة، وبعضها مخصص للسياسات البرمجية فقط.

## 2. تصنيف البنود قبل اختيار أداة التقييم

هذه خطوة حاسمة؛ إذ ينبغي أن تتناسب أداة التحقق مع طبيعة البند.

| نوع البند            | الوصف                             | أداة التحقق المناسبة                   |
| -------------------- | --------------------------------- | -------------------------------------- |
| Behavioral Policy    | ضبط سلوك النموذج                  | Promptfoo واختبارات سلوكية             |
| Research Methodology | تحديد خطوات البحث والاستدلال      | فحص التغطية والأدلة والمراجعة المتخصصة |
| Access Control       | تحديد السماح والمنع والصلاحيات    | OPA أو Cedar                           |
| Workflow Rule        | تنظيم الحالات وانتقالاتها         | State Machine Tests                    |
| Evidence Requirement | اشتراط أدلة للتحقق والاعتماد      | Validators وسجلات الأدلة               |
| Governance Procedure | تنظيم التفويض والمراجعة والاعتماد | Decision Ledger ومراجعة بشرية          |

النتيجة: لا يوجد محرك واحد يغطي جميع هذه الأنواع بصورة مناسبة.

## 3. أفضل الأدوات بحسب الوظيفة

| الأداة                | الغرض الأساسي                                    | توصية الاستخدام                   |
| --------------------- | ------------------------------------------------ | --------------------------------- |
| Excel / Google Sheets | جرد البنود والتصفية والتقييم وقرارات المالك      | البداية العملية                   |
| AAPES v2.1            | منهجية جودة المتطلبات والتتبع والأوزان والبوابات | المرجع الهندسي                    |
| Promptfoo             | تقييم سلوك النموذج ومقارنة نسخ التعليمات         | مهم للبنود السلوكية               |
| Open Policy Agent     | اختبار سياسات السماح والمنع المكتوبة بـRego      | متخصص للصلاحيات والضوابط البرمجية |
| Conftest              | اختبار ملفات JSON وYAML والتكوينات               | مناسب للبنود المهيكلة             |
| Cedar                 | تحليل سياسات التفويض وتغيرات الصلاحيات           | مناسب عند استخدام Cedar           |
| NetworkX              | تحليل شبكة العلاقات والتبعيات والتداخل           | مفيد لمجموعات البنود الكبيرة      |
| Decision Ledger       | تسجيل قرارات المالك والمبررات والأدلة            | أساسي للحوكمة                     |

أما أدوات مثل `rule-lab` و`IBM Smith` و`SynomosAI` و`AISM Decision Card`، فيمكن النظر فيها كمرشحات إضافية، لكن لا أنصح بجعل أي منها اعتمادًا أساسيًا قبل التحقق من المشروع المحدد، وصيانته، وترخيصه، وتوافقه مع نوع القواعد، والوظائف التي يضيفها فعلًا.

يمكن الاطلاع على المراجع الرئيسية من مواقعها: [OPA](https://www.openpolicyagent.org/?utm_source=chatgpt.com)، [Cedar](https://www.cedarpolicy.com/?utm_source=chatgpt.com)، [Conftest](https://www.conftest.dev/?utm_source=chatgpt.com)، [Promptfoo](https://www.promptfoo.dev/?utm_source=chatgpt.com).

## 4. ما الوظائف التي أوصي بإنشائها؟

بدل إنشاء أداة لمراجعة النصوص فقط، أوصي بست وحدات وظيفية:

| الوحدة                           | وظيفتها                                   | الأولوية |
| -------------------------------- | ----------------------------------------- | -------- |
| Rules Inventory & Classification | تصنيف البنود ومجالاتها وسلطتها وحالتها    | P0       |
| Rule Review Workbench            | مراجعة البند وتفاصيله وصياغاته            | P0       |
| Merge & Conflict Analyzer        | اكتشاف التكرار والتكافؤ والتعارض والتداخل | P0       |
| Impact & Dependency Analyzer     | تحديد أثر تعديل أو دمج أو إزالة بند       | P0       |
| Owner Decision Ledger            | تسجيل القرارات والموافقات والتأجيلات      | P0       |
| Evaluation & Experiment Lab      | اختبار أثر القواعد وصياغاتها وبدائلها     | P1       |

يمكن بناء واجهة تعرض العلاقات في رسم بياني، بحيث تختار بندًا فتظهر البنود المرتبطة به ومصادرها وسبب العلاقة.

وينبغي التمييز بصريًا بين علاقة مثبتة من بنية البيانات، وعلاقة اقترحها نموذج لغوي ولم تُراجع بعد.

## 5. نموذج تفاعلي لفرز قرارات المالك

هذا مثال لكيفية تنظيم قائمة المراجعة داخل واجهة مستقبلية.

ما نوع القرار الذي تريد مراجعته؟

دمج أو تجميع بنود

حسم تعارض

تحسين أو تقسيم

اعتماد أو تأجيل

### MERGE / CONSOLIDATE

راجع تكافؤ السلوك والسلطة والنطاق والاستثناءات، وحافظ على جميع الالتزامات والاختبارات الأصلية.

وجود علاقات واضحة بين البنود

عدم فقدان متطلبات أو استثناءات

وجود صياغة موحدة قابلة للاختبار

الحالة المتوقعة: مرشح دمج — لا يطبّق إلا بعد المراجعة والاختبار والاعتماد

هذه محاكاة توضيحية لطريقة إدارة القرارات، وليست مرتبطة بملف البنود الفعلي.

## 6. كيف تقيس نجاح عملية الدمج والتحسين؟

هناك خطأ شائع ينبغي تجنبه: اعتبار انخفاض عدد البنود دليل نجاح.

قد ينخفض العدد من 423 إلى 200، لكن تختفي معه قيود مهمة أو تصبح البنود طويلة ومركبة وصعبة الاختبار.

أوصي بالمقاييس التالية:

| المقياس                  | ما الذي يوضحه؟                                 |
| ------------------------ | ---------------------------------------------- |
| Coverage Preservation    | نسبة الالتزامات الأصلية التي بقيت مغطاة        |
| Redundancy Reduction     | مقدار التكرار الذي أزيل                        |
| Conflict Resolution Rate | نسبة التعارضات التي حُسمت                      |
| Atomicity Compliance     | نسبة المتطلبات الذرية                          |
| Testability Coverage     | نسبة البنود ذات معايير القبول القابلة للاختبار |
| Critical Violation Rate  | معدل انتهاك القيود الحرجة في الاختبارات        |
| False Refusal Rate       | معدل رفض السلوك المسموح                        |
| Operational Overhead     | الزمن والتكلفة والتعقيد التشغيلي               |

ولا توجد أرقام فعلية لهذه المقاييس في المعطيات الحالية. يجب حسابها من البنود الأصلية ونتائج الاختبارات، لا من تقديرات النموذج وحدها.

# ثالثًا: خارطة التنفيذ المقترحة لمراجعة البنود الـ423

أقترح تنفيذ العمل على أربع مراحل متسلسلة:

01 — Inventory & Classification

تثبيت العدد والمعرفات وتصنيف البنود والمصادر والسلطة

02 — Rule Relationships

اكتشاف التكرار والتكافؤ والتعارض والتبعيات ومجموعات الدمج

03 — Owner Review Workspace

عرض البطاقات والمقارنات والأثر والأدلة وتسجيل القرارات

04 — Controlled Evaluation

اختبار الصياغات والتحسينات واعتماد القرارات ضمن النطاق

أبدأ عمليًا باستخدام ملف Excel الحالي وبناء مصفوفة علاقات وقرارات مرتبطة به؛ ولا حاجة في البداية إلى تطبيق كبير أو محرك تنفيذ كامل.

وبعد التأكد من أن التحليل والمراجعات مفيدان، يمكن إنشاء واجهة مستقلة تعتمد على قاعدة بيانات منظمة وتستورد ملفات Excel، وتصدر نتائجها إليها.

## النتيجة النهائية التي أوصي بها

أرى أن المخرج المستهدف ليس ملفًا يحتوي على عدد أقل من البنود، بل سجلًا معياريًا محكومًا (Governed Policy Registry) يحقق ما يلي:

- لكل بند هوية وسلطة ونطاق ومبرر وأهمية وأثر وحالة تحقق.
- لكل علاقة أو دمج دليل وتفسير واختبارات وعدم فقدان للالتزامات.
- لكل تعديل نسخة أصلية ومقترح وفرق واضح.
- لكل قرار موافقة محددة النطاق وصاحب صلاحية وتاريخ.
- لكل أثر تمييز بين المتوقع والمقاس.
- لكل قاعدة حرجة آلية إنفاذ أو فجوة واضحة تمنع الادعاء بالجاهزية.

توصيتي الحاسمة: ابدأ بـمحرك تحليل العلاقات وإمكانية الدمج (Rule Relationship & Merge Analysis)، يتبعه Owner Review Workspace. هاتان الوظيفتان ستقدمان أعلى قيمة مباشرة في مراجعة مجموعة كبيرة من البنود، قبل التوسع في أدوات التنفيذ والقياس المتقدمة.

ولا ينبغي تفويض الوكيل بحذف البنود أو دمجها فعليًا منذ البداية؛ بل يُكلف أولًا بإنتاج مرشحات دمج وتحسين قابلة للمراجعة مع أدلتها، ثم تقرر أنت اعتمادها أو تعديلها أو رفضها.

أوصي بتطوير واجهة مستقلة وظيفيًا داخل AGHR Governance Studio باسم `Owner Governance Cockpit`، تكون مركزك لاتخاذ قرارات اعتماد القواعد وتحسينها ودمجها وإيقافها.

لا تحتاج بصفتك المالك إلى مراجعة كود كل قاعدة أو تفاصيل JSON وYAML. ما تحتاج إليه هو القدرة على الإجابة عن ستة أسئلة:

1. لماذا وُضع هذا البند؟ وهل ما زال ضروريًا؟
2. ما مصدر سلطته، وما مستوى إلزامه؟
3. ما الذي يمنعه أو يفرضه عمليًا؟
4. ما أثر تعديله أو حذفه أو دمجه مع بند آخر؟
5. هل أثبتت الاختبارات فائدته، أم أن فائدته مفترضة فقط؟
6. هل ينبغي الإبقاء عليه أو تحسينه أو دمجه أو تعطيله أو طلب مزيد من الأدلة؟

الأهم: يجب أن يقدّم النظام لك توصيات مدعومة بالأدلة، بينما تحتفظ أنت بسلطة اتخاذ القرارات التي تتطلب موافقة المالك.

## 1. ما الأدوات التي يوفرها مشروعك حاليًا؟

راجعت المكونات المصدرية الموجودة في المستودع، وهذه أهم الوظائف ذات الصلة.

توجد نقطة مهمة في `server/comparison.js`: تحليل أثر البند يبحث حاليًا عن البنود التي تشترك معه في مرجع أو أساس سلطوي، ويعيد جزءًا من العلاقات المكتشفة. هذا تحليل ارتباط بنيوي، وليس إثباتًا لما سيحدث إذا حُذف البند أو دُمج.

وكذلك تؤكد وثائق القياس في المشروع أن الملاحظة المقاسة الحالية تخص استقرار حالة مرجعية محددة، ولا تثبت أثرًا سببيًا عامًا لبقية القواعد.

إذن لدينا أساس جيد، لكن ينقصه نظام متكامل يساعدك في اتخاذ قرار بشأن كل بند ومجموعات البنود.

وأفضّل أن تظهر البطاقة أيضًا النص الأصلي، والصياغة المقترحة، والمصدر، وحالة التنفيذ، والاختبارات، وسبب التوصية.

## 3. كيف نقرر إمكانية دمج بندين؟

لا أنصح باستخدام التشابه النصي وحده لاتخاذ قرار الدمج. فقد تتشابه قاعدتان في الكلمات، لكنهما تؤديان وظيفتين مختلفتين.

أقترح أن يمر كل دمج بخمس مراجعات:

1. هل الهدف والسلوك المطلوب متكافئان؟
2. هل مستوى السلطة والإلزام متوافقان؟
3. هل النطاق والشروط والاستثناءات متطابقة أو قابلة للتوحيد؟
4. هل يترتب على الدمج فقدان ضابط مستقل أو اختبار أو دليل؟
5. هل نجح البند الموحد في جميع اختبارات البندين، بما فيها الحالات السلبية والحدية؟

### مثال عملي

| البند    | النص                                                             |
| -------- | ---------------------------------------------------------------- |
| RULE-101 | يمنع تعديل قاعدة الإنتاج دون موافقة موثقة                        |
| RULE-102 | لا يجوز تنفيذ عمليات كتابة إنتاجية قبل التحقق من صلاحية الموافقة |
| RULE-103 | يجب تسجيل كل عملية كتابة إنتاجية في سجل التدقيق                  |

البندان 101 و102 متقاربان، لكنهما ليسا متطابقين تمامًا. الأول يقرر شرط الموافقة، والثاني يلزم بالتحقق من صلاحيتها قبل التنفيذ.

القرار المقترح: يمكن دراسة توحيدهما في مواصفة مشتركة، مع إبقاء الالتزامين قابلين للاختبار بصورة مستقلة. أما RULE-103 فهو ضابط تدقيق مختلف، ولا ينبغي حذفه باعتباره تكرارًا.

وهنا تحتاج واجهة الدمج إلى عرض النتائج التالية:

| الخيار        | نتيجة المراجعة                               |
| ------------- | -------------------------------------------- |
| MERGE         | تكافؤ مثبت مع الحفاظ على جميع الالتزامات     |
| CONSOLIDATE   | تجميع تنظيمي مع بقاء المتطلبات الذرية مستقلة |
| KEEP SEPARATE | وظائف مختلفة رغم التشابه                     |
| CONFLICT      | تعارض يحتاج حسم السلطة                       |
| INCONCLUSIVE  | أدلة غير كافية لاتخاذ القرار                 |

ويجب أن يحتفظ النظام بعلاقات المعرفات الأصلية `supersedes` و`derived_from`، ولا ينفذ حذفًا ماديًا تلقائيًا.

## 4. كيف نعرف أثر البند فعلًا؟

أنصح بعرض ثلاثة أنواع منفصلة من الأثر:

| نوع الأثر                  | السؤال                                    | طريقة قياسه                    |
| -------------------------- | ----------------------------------------- | ------------------------------ |
| Structural Impact          | ما القواعد والاختبارات والملفات المتأثرة؟ | تحليل التبعيات والعلاقات       |
| Expected Risk Impact       | ما الخطر المحتمل عند حذف أو إضعاف البند؟  | تحليل المخاطر والضوابط والسلطة |
| Measured Behavioral Impact | هل يغير البند سلوك الوكيل فعلًا؟          | اختبارات A/B وAblation         |

النوع الثالث هو الأصعب والأكثر أهمية.

مثلًا، إذا كان لدينا بند يمنع الوكيل من اعتماد نتائج بلا أدلة، فيمكن اختبار مجموعة الحالات نفسها بثلاث نسخ: القاعدة الأصلية، وقاعدة معدلة، ونسخة مرجعية معزولة لا تحتوي على القاعدة حيث يكون التعطيل آمنًا داخل الاختبار.

نقيس حينها معدل الادعاءات الكاذبة والرفض الخاطئ والالتزام بالشروط. لكن لا ينبغي تنفيذ اختبار إزالة قاعدة أمنية على الإنتاج.

ويجب فصل الأثر المتوقع عن الأثر المقاس، وألا نعرض نسبة تحسن ما لم تُجرَ التجربة فعليًا.

## 6. كيف ينبغي أن تكون دورة عملك كمالك؟

1\. Review Queue

استعراض البنود المقترحة للمراجعة بحسب الأولوية والأثر

2\. Rule Detail

قراءة النص والهدف والسلطة والنطاق ودليل الحاجة

3\. Relationship & Merge

مقارنة البنود المتشابهة والتعارضات والتبعيات

4\. Impact & Tests

مراجعة الأثر المتوقع والنتائج التجريبية المتاحة

5\. Owner Decision

إصدار قرار معلل: إبقاء أو تحسين أو دمج أو تأجيل

6\. Governed Change Package

إنشاء طلب تغيير قابل للتنفيذ والتحقق دون تفعيل تلقائي

أقترح أن يكون تصرفك الطبيعي هو اعتماد قرار بشأن التغيير المقترح، وليس تعديل الملفات بنفسك. يستطيع الوكيل بعد ذلك إعداد التغيير واختباره، لكن الانتقال إلى الإصدار الرسمي أو التفعيل يبقى قرارًا منفصلًا.

## 7. الإضافة الأهم إلى طلب تطوير المشروع

أوصي بإضافة مرحلة مستقلة باسم:

Owner Governance Review & Decision Workspace — OGR-01

وتشمل مبدئيًا أربع وظائف حرجة:

- `Rule Detail & Review`: بطاقة غنية بالبند والأدلة والتوصيات.
- `Merge & Conflict Advisor`: مقارنة البنود وإثبات صلاحية الدمج قبل اقتراحه.
- `Impact Preview`: تحليل أثر التغييرات وإظهار ما هو مقاس وما هو مجرد توقع.
- `Owner Decision Ledger`: تسجيل قرارات المالك وأسبابها وبصمات النسخ التي تنطبق عليها.

ويجب أن تكون هذه الوظائف امتدادًا لشاشات AGHR الموجودة، لا منصة مستقلة جديدة. كما ينبغي أن تكون واجهة المالك بالعربية والإنجليزية، مع تصفية البنود بحسب المجال والنطاق والأهمية ومستوى الخطورة وحالة التحقق.

### التوصية النهائية

لو كنت أحدد ما يُنفذ أولًا، فسأبدأ بـبطاقة مراجعة البند، ومستشار الدمج، ومعاينة أثر التغيير. هذه الثلاثة ستتيح لك مراجعة البنود واتخاذ قرارات ذات قيمة مباشرة، قبل الاستثمار في تحسينات الرسوم البيانية ولوحات المؤشرات.

والأهم أن يظل النظام واضحًا في ثلاث حالات: ما يعرفه من النصوص والبنية، وما يستنتجه، وما أثبته بالاختبارات. فهذا هو الفرق بين واجهة مراجعة جذابة ومنصة تدعم قرارات حوكمة موثوقة.

Subsumption	بند عام يتضمن بندًا أكثر تخصصًا	ربط هرمي أو توحيد مشروط
Complementary	بندان متكاملان لكنهما مستقلان	تجميع تنظيمي دون حذف أحد الالتزامين
Conflict	البندان ينتجان قرارات غير متوافقة في حالة مشتركة	حسم السلطة والنطاق قبل أي دمج

وأوصي بالتفريق بين:
- دمج تنظيمي (Consolidation): وضع بنود مترابطة تحت سياسة أو مجال واحد.
- دمج معياري (Normative Merge): استبدال التزامات أصلية بالتزام أو مجموعة التزامات جديدة مع إثبات عدم فقدان أي واجب أو حظر أو استثناء.
الأول أسهل وأقل مخاطرة. الثاني يحتاج فحص التكافؤ والتغطية والتأثير.
مثال من النص الذي عرضته
ورد اقتراح تقسيم QL4-A01 إلى تعريف هوية المتن وفحص أهلية المصدر.

أؤيد منطق التقسيم إذا كان البند يجمع بالفعل بين واجبين مستقلين؛ لأن التحقق من هوية المصدر لا يثبت تلقائيًا أهلية اعتماده.

لكنني لم أراجع نص QL4-A01 الأصلي، لذا فهذا قبول لمبدأ هندسي وليس اعتمادًا فعليًا لقرار تقسيم ذلك البند.
4. ما الذي ينبغي أن يظهر لك في واجهة المالك؟
أوصي بأن يعرض AGHR أربعة مستويات من المعلومات لكل بند، بدل درجة جودة واحدة:
نموذج مقترح لبطاقة القرار
ضرورة البند

ما المخاطرة أو الفجوة التي يعالجها؟


جودة البند

هل هو واضح وذري ومتسق؟


الأثر

ما التبعيات والنتائج والتكلفة؟


قوة الأدلة

مفترض، مستنتج، مختبر، أم متحقق استقلاليًا؟




هذه عناصر تصميمية مقترحة للواجهة، وليست مقاييس مُنفذة أو نتائج فعلية.

وأضيف حقلًا مهمًا: أثر عدم وجود البند (Impact of Absence). فهو يجيب عن سؤال مختلف عن جودة صياغته: ماذا نخسر إذا حذفناه؟

قد يكون البند مكتوبًا بصورة ضعيفة لكنه يحمي ثابتًا حرجًا؛ فيستحق إعادة الصياغة، لا الحذف. وقد يكون مكتوبًا بصورة ممتازة لكنه لا يضيف حماية أو فائدة فوق بند آخر.
5. كيف تبدأ مراجعة 423 بندًا دون استهلاك وقتك؟
أوصي باستخدام أربع مراحل، على أن ينفذ الوكيل التحليل ويعرض عليك القرارات فقط.
1. الجرد والتصنيف الآلي

   تثبيت العدد والمعرفات والمصادر، وتصنيف المجالات والسلطة والمخاطر، واكتشاف البنود المتطابقة والناقصة.
2. استخراج مجموعات القرار

   تجميع المقترحات إلى: تعارضات تحتاج مالكًا، مرشحات دمج، بنود مركبة تحتاج تقسيمًا، صياغات محسنة، وفجوات غير مغطاة.
3. مراجعة مرتبة بحسب المخاطر

   البدء بالتعارضات المؤثرة وبنود P0، ثم مراجعة مجموعات الدمج عالية الثقة، بدل قراءة كل بند على حدة.
4. التقييم والاعتماد

   اختبار المرشحات، ثم عرض الفرق والأدلة عليك لاعتماد المواصفات. يبقى تنفيذ التغييرات وتفعيلها ضمن إجراءات منفصلة.

ولا أنصح بأن يكون هدف المرحلة تقليل العدد 423 إلى عدد أصغر بأي ثمن. المقياس الأفضل هو تقليل التكرار والتعارض وعبء الإدارة مع المحافظة على التغطية والالتزامات الضرورية.
6. تصحيح مهم في صلاحيات المالك
ذكر المقترح أنك تستطيع حسم ما إذا كان البند MUST أو SHOULD أو MAY. هذا صحيح في حدود سلطتك، لكنه يحتاج ضبطًا:

قرار تخفيف الإلزام يجب أن يستند إلى طبيعة المتطلب والمخاطر ومصدر سلطته، وليس إلى الرغبة في تسهيل التنفيذ. كذلك، لا يجوز تغيير قاعدة مستمدة من مرجع أعلى اعتمادًا على قرار محلي لا يملك سلطة استبدالها.

وأوصي بالفصل بين أربع موافقات:
القرار	دلالته
APPROVE_SPEC	اعتماد الصياغة والمعنى
APPROVE_TEST_PLAN	اعتماد معايير الاختبار وتغطيته
ACCEPT_RESIDUAL_RISK	قبول مخاطر متبقية محددة ضمن سلطة المالك
AUTHORIZE_ACTIVATION	التصريح بالتفعيل بعد استيفاء الشروط

لا تمنح واحدة منها الموافقات الأخرى تلقائيًا.

7. قراري النهائي بشأن المقترح
أوصي باعتماد الاتجاه الإداري والمنهجي، لكن مع تغيير ترتيب التنفيذ:
الأولوية	ما أنصح بتنفيذه داخل AGHR
P0	Owner Decision Queue — قائمة قرارات المالك المعلقة
P0	Rule Relationship & Merge Analyzer — تحليل العلاقات والتكرار وإمكانية الدمج
P0	Rule Impact Preview — عرض التبعيات والآثار المتوقعة والأدلة
P0	Decision Ledger — سجل قرارات المالك والإصدارات
P1	Rule A/B & Ablation Evaluation — قياس الأثر الفعلي في بيئة معزولة
P2	OPA/Cedar/Smith Integration — أدوات متخصصة للسياسات البرمجية فقط

لا أرى ضرورة لإنشاء منصة أخرى أو اعتماد جميع الأدوات المقترحة. فمشروع AGHR يحتوي بالفعل على سجل البنود، وشاشات التفاصيل، وخدمات المقارنة والتقييم والتغيير والتدقيق. المطلوب هو تطوير هذه المكونات لتصبح بيئة قرارات قوية للمالك.

أما ملف Excel، فأوصي بالإبقاء عليه كوسيلة للاستيراد والتصدير والمراجعة الجماعية، وليس أن يصبح مصدرًا موازيًا للحقيقة ينافس قاعدة بيانات Studio.

الخطوة التالية الأكثر قيمة: تكليف وكيل AGHR بإعداد Owner Governance Cockpit على أساس البنود الـ423، بدءًا بعرض مجموعات البنود المتشابهة والمتعارضة، وبطاقات تأثيرها، وقرارات الدمج المحتملة، دون السماح بأي حذف أو دمج فعلي قبل اعتمادك.

وبذلك تنتقل من إدارة 423 نصًا إلى إدارة مجموعة قرارات حوكمة واضحة ومرتبة ومدعومة بالأدلة.
